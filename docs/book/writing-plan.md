## 二、核心逻辑切片（微观视角）

### 2.1 领域模型与类型定义

#### 核心实体关系

```
Project (项目)
    ├── id: string
    ├── worktree: string
    └── vcs: "git" | undefined

Instance (实例) - 每个项目目录一个
    ├── directory: string
    ├── project: Project
    └── state: Map<Symbol, any>  // 隔离状态

Session (会话)
    ├── id: Identifier
    ├── title: string
    ├── agent: string
    ├── model: { providerID, modelID }
    ├── permission: Ruleset
    └── messages: Message[]

Message (消息)
    ├── id: Identifier
    ├── role: "user" | "assistant"
    └── parts: Part[]

Part (消息部分)
    ├── type: "text" | "tool_call" | "tool_result" | ...
    └── content: any

Agent (代理)
    ├── name: string
    ├── mode: "primary" | "subagent"
    ├── permission: Ruleset
    └── prompt: string

Permission.Rule (权限规则)
    ├── permission: string
    ├── pattern: string
    └── action: "allow" | "deny" | "ask"
```

### 2.2 高复用/高复杂度工具

#### 工具系统架构

```typescript

export const BashTool = Tool.define("bash", async () => {
  return {
    description: "...",
    parameters: z.object({ ... }),
    async execute(params, ctx) {
      // 1. 权限检查
      await ctx.ask({ permission: "bash", patterns: [...] })
      // 2. 执行命令
      const proc = spawn(params.command, { shell, cwd })
      // 3. 流式输出
      proc.stdout?.on("data", (chunk) => ctx.metadata({ ... }))
      // 4. 返回结果
      return { title, metadata, output }
    }
  }
})
```

### 3.2 关键设计决策

#### 决策 1: 为什么选择 EventBus？

**问题**: 模块间如何通信？

**方案对比**:
| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接调用 | 简单直接 | 紧耦合 |
| 依赖注入 | 可测试 | 复杂度高 |
| EventBus | 松耦合，可观测 | 调试困难 |

**最终选择**: EventBus

**理由**:
1. AI 编码助手需要处理大量异步事件（流式输出、工具调用、权限请求）
2. 模块间需要解耦（Session 不应该知道 TUI 的存在）
3. 便于调试和监控（所有事件可追踪）

**Trade-off**: 调试复杂度增加，需要事件链路追踪工具

#### 决策 2: 为什么使用 Instance 隔离？

**问题**: 如何支持多项目并行？

**方案对比**:
| 方案 | 优点 | 缺点 |
|------|------|------|
| 全局状态 | 简单 | 状态污染 |
| 实例隔离 | 安全隔离 | 内存开销 |

**最终选择**: 实例隔离

**实现**:
```typescript
// 使用 Symbol 作为状态键
const state = Instance.state(() => ({
  sessions: new Map(),
  tools: []
}))
```

**理由**:
1. 用户可能在多个终端窗口运行 OpenCode
2. 不同项目的配置、会话、权限应该隔离
3. 实例销毁时自动清理资源

#### 决策 3: 为什么选择 Zod？

**问题**: 如何保证配置和 API 的类型安全？

**方案对比**:
| 方案 | 编译时 | 运行时 | 学习成本 |
|------|--------|--------|---------|
| TypeScript 接口 | ✅ | ❌ | 低 |
| JSON Schema | ❌ | ✅ | 中 |
| Zod | ✅ | ✅ | 中 |

**最终选择**: Zod

**理由**:
1. 配置文件需要运行时验证（用户可能写错）
2. API 响应需要运行时验证（AI 输出不可信）
3. 自动生成 TypeScript 类型

### 3.3 边缘案例与 Bug 修复

#### 案例 1: 权限检查的竞态条件

**问题**: 用户快速点击 "允许" 时，可能触发多次权限请求

**解决方案**:
```typescript
// 使用 pending Map 存储待处理请求
const s = await state()
s.pending[id] = { info, resolve, reject }
// 后续相同请求直接复用
```

#### 案例 2: LSP 服务器的生命周期

**问题**: LSP 服务器可能启动失败或崩溃

**解决方案**:
```typescript
// 使用 broken Set 记录失败的服务器
if (s.broken.has(root + server.id)) continue
// 失败后不再重试，避免无限循环
```

#### 案例 3: 会话消息的增量更新

**问题**: 长会话的消息列表可能很大

**解决方案**:
```typescript
// 使用流式读取，避免一次性加载
export async function* messages(sessionID) {
  for await (const msg of MessageV2.stream(sessionID)) {
    yield msg
  }
}
```

```typescript
while (true) {
  const result = await streamText({ model, messages, tools })
  
  // 处理文本输出
  for await (const chunk of result.textStream) {
    process.stdout.write(chunk)
  }
  
  // 检查是否有工具调用
  const toolCalls = result.toolCalls
  if (toolCalls.length === 0) break
  
  // 执行工具
```

## 五、写作规范

### 5.1 每节结构

```markdown
### X.Y 节标题

**目标**: 具体输出

**问题**: 为什么需要这个？

**方案对比**:
| 方案 | 优点 | 缺点 |
|------|------|------|

**最终选择**: ...

**代码伴读**:
\`\`\`typescript
// Context: 文件位置
// Problem: 解决什么问题
// Insight: 设计原则
\`\`\`

**练习**: 读者实现任务

**技术难点**: 独立总结

**企业级价值**: 实际应用场景
```

### 5.2 代码展示原则

1. **最小化**: 只展示决策相关代码
2. **上下文**: 说明文件位置和作用
3. **演进**: 展示 before/after 对比
4. **注释**: 只在必要时添加

### 5.3 禁止模式

- ❌ 逐行解释代码
- ❌ 完整文件堆砌
- ❌ 无上下文的代码片段
- ❌ 跳过问题直接给答案
